# M2 사전 검증 — 조건부 진행

요약: Semgrep CE 1.186.0의 네이티브 엔진과 로컬 규칙이 합성 JS/TS에서 동작했다. 결과 스키마와 어댑터 단위 테스트에 착수할 근거는 확보했다. 일반 사용자에게 배포할 컨테이너와 제품 실행기는 아직 인수되지 않았다.

## 고정한 실험 환경
- 호스트: Intel macOS, Docker Engine 20.10.20, linux/amd64 컨테이너. 해당 버전의 공식 PyPI 배포 목록에 Intel macOS wheel이 없다. 소스 빌드는 검증하지 않았다.
- 엔진: 공식 manylinux_2_34_x86_64 wheel SHA-256 `54ebaf79adf4e5855c54d5e4457d8d03f27cc6bf73d79642281790b833d92e4f`. 내부 bin 디렉터리 전체를 사용하고 osemgrep → semgrep-core 링크를 생성했다. 네이티브 CLI에는 scan --experimental이 필요했다. Python CLI와 동일하다고 가정하지 않는다. [공식 배포 메타데이터](https://pypi.org/pypi/semgrep/1.186.0/json)
- 런타임: 기존 로컬 Linux 이미지 ID `sha256:48313211fa441a6552e6f6471ae8c991b9a66d5581161b685fa143e79c46ac77`. 이 이미지는 사전 검증용이다. 공식 Docker 이미지 다운로드가 레이어 재시도를 반복해 이 경로로 검증했다.
- 규칙: 사전 검증 스크립트에서 직접 생성한 두 패턴. Registry 규칙 및 그 라이선스는 가져오지 않았다. 직렬화한 규칙 파일 SHA-256 `a9c3a1412cc42eacde18f74084430b049c182d5682b6c2c1ea0937c35f1c532b`. 엔진 라이선스와 향후 채택할 외부 규칙 라이선스는 따로 기록한다. [공식 라이선스 안내](https://semgrep.dev/blog/2024/important-updates-to-semgrep-oss/)
- 격리: 로컬 이미지 ID, pull 금지, 네트워크 none, UID 65534, 읽기 전용 루트·엔진·입력, 호스트 소켓 없음. 1 CPU, 메모리 768 MiB, PID 96, 쓰기 가능한 /tmp는 96 MiB tmpfs. 메트릭과 버전 체크 비활성화. 입력 쓰기 거부, 임시 파일 쓰기 가능, IPv4 라우팅 테이블에 경로 없음, Docker 소켓 부재를 컨테이너 내부에서 확인했다. [메트릭 문서](https://docs.semgrep.dev/metrics)

## 재현
먼저 공식 wheel을 SHA-256으로 검증한다. wheel의 semgrep/bin/ 아래를 .cache/m2/bin/에 추출하고 semgrep-core에 실행 권한을 준 뒤 같은 디렉터리에 osemgrep 심볼릭 링크를 둔다. 이 체크아웃의 로컬 캐시는 준비됐다. 아래 스크립트는 엔진과 합성 입력 전용 임시 폴더만 읽기 전용으로 마운트한다.
```sh
python3 evaluation/m2/preflight.py .cache/m2/bin sha256:48313211fa441a6552e6f6471ae8c991b9a66d5581161b685fa143e79c46ac77
```

| 입력 | 실제 종료 | JSON 결과 | 제품에서 사용할 해석 |
|---|---:|---|---|
| 서버 응답에 요청 값을 직접 전달 / 브라우저 HTML 속성 대입 | 1 | 2파일 검사, 예상 규칙·위치 2건 | 취약 가능 패턴. 호출 문맥과 데이터 신뢰도 확인 |
| 같은 합성 입력을 일반 텍스트 응답 / textContent로 변경 | 0 | 2파일 검사, 0건 | 이 두 규칙에 대해 검사 완료 |
| 지원 소스 파일 없음 | 0 | 검사 파일 0, 발견 0 | 미지원 또는 미검사 |
| 잘못된 규칙 스키마 | 7 | 오류 1, 검사 파일 0 | 도구 실패 |

표는 엔진/격리 호환성 실험이다. 2건은 실제 Juice Shop 탐지율이 아니다. 제품은 원본 JSON의 소스 조각을 그대로 내보내지 않고 규칙 ID·상대경로·행·통제된 권고만 노출한다.

## 구현 진입과 남은 인수 기준
1. M1 scan의 출력 스키마·종료 코드를 보존한다. M2 결합 모드는 명시적으로 선택하게 하고, 도구별 결과 및 완료 상태를 가진 별도 버전의 보고서를 정의한다. 기존 CLI 단위 테스트는 재통과했다.
2. 디코더부터 구현할 수 있다. 입력 인벤토리와 실제 검사 파일의 차이, 일부 파일 파싱 실패, 유효하지 않은 JSON, 시간 제한/컨테이너 정리, OSV 성공과 Semgrep 실패가 동시 발생한 경우를 실제 CLI 인수 기준에 넣는다.
3. 제품용 이미지의 immutable digest, 출처, 네이티브 엔진과 CLI 버전을 확정하고 깨끗한 환경에서 같은 검사를 재현한 뒤 실행기를 붙인다. 개발자의 기존 이미지 ID는 이 전제의 대체물이 아니다. M1 호스트 격리 실행기에 Docker 소켓 접근 권한을 추가하지 않는다.
4. M0 사례는 목록 공개와 운영 지표 접근 통제에 관한 것이다. 이번 두 합성 규칙은 다른 위험을 보므로 같은 분모로 집계하지 않는다. 서버 입력/브라우저 출력 규칙은 각각 독립적인 보류 사례와 동등한 안전 코드로 평가한다. M0 공식 보류 세트는 제품 규칙 해시를 고정한 후 한 번 평가하고 범위 밖/누락을 별도로 기록한다.
